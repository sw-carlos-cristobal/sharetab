# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

ShareTab — open-source, self-hosted Splitwise alternative with AI receipt scanning. Targets Unraid (Docker).

## Tech Stack

- **Framework:** Next.js 16 (App Router) + TypeScript
- **API:** tRPC v11 (end-to-end type-safe)
- **ORM:** Prisma 7 + PostgreSQL 16 (via `@prisma/adapter-pg`); `npm run dev:full` runs embedded PostgreSQL 18 (`embedded-postgres`), so local dev is two majors ahead of Docker and CI
- **Auth:** NextAuth v5 (email/password + magic link + Google + generic OIDC)
- **UI:** TailwindCSS 4 + shadcn/ui (v4, uses `@base-ui/react` — use `render` prop instead of `asChild`) + next-themes (dark mode)
- **AI:** Pluggable providers (OpenAI, OpenAI-Codex, Claude, Meridian, Ollama) via `src/server/ai/`
- **i18n:** next-intl (9 locales: en, es, sv, fr, de, pt-BR, ja, zh-CN, ko)

## Architecture

- `src/server/` — Backend: auth config, Prisma client, tRPC routers, AI providers, pure calculation libs
- `src/server/db.ts` — Prisma client singleton (uses `@prisma/adapter-pg` with `PrismaPg`, on the pool from `src/server/lib/db-pool.ts`, whose connections set `search_path` to `public` so raw SQL's unqualified table names find Prisma's tables whatever the role or `DATABASE_URL` sets)
- `src/server/auth.ts` — NextAuth v5 config (Credentials unless `DISABLE_PASSWORD_LOGIN` + optional Google OAuth + optional Nodemailer magic link + optional generic OIDC); wraps the Prisma adapter so `getUserByEmail` is case-insensitive. The generic OIDC provider registers with `checks: ['pkce', 'state']`: Auth.js's default for a generic provider is `['pkce']`, which sends no `state`, and Cloudflare Access rejects such an authorization request with `invalid_request: state is a required parameter`. It sets `trustHost: true`, so Auth.js never reads `AUTH_TRUST_HOST` (#417; why is in the comment there, and `src/server/trust-host.test.ts` runs the setting through the real Auth.js); without `AUTH_URL`/`NEXTAUTH_URL`, magic links, Google/OIDC callbacks and the page Sign out returns to point at the server's listening address (`0.0.0.0:3000` in the image), while password sign-in works without one. A password reset or change ends every session signed in under the old password (#397): the `jwt` callback puts the user's `passwordChangedAt` at sign-in on the token (`passwordStamp`; password login passes the value it read with the hash it verified, so a sign-in racing a reset ends too) and, whenever it runs (`auth()`, the session endpoint), returns null when the user's current value differs; `auth()` then reports no session and the session endpoint clears the cookie. Tokens from before the stamp count as 0, so nobody is signed out until their password changes. When the callback can't read the user's version (a database error), the session counts as ended too, so every caller of `auth()` refuses it for that request (a sign-in keeps its own session: its provider just read the version). Only the session endpoint would clear the cookie (`SessionProvider` reads it whenever a page loads or a tab becomes visible, and tells the browser's other tabs to read it too); the Auth.js route wraps it with `keepSessionWhileDatabaseDown` (`src/server/lib/session-endpoint.ts`): when the callback's read failed it calls `markPasswordVersionUnread`, which the wrapper sees through an `AsyncLocalStorage` scoped to the request, and an answer that would clear the cookie becomes a 503 with the cookie left alone, so a database outage signs nobody out. A session that really ended still has its cookie cleared. The middleware's `getToken` doesn't run the callback, so an ended session still passes it until a page or API call checks. Because Auth.js itself decodes the cookie when linking a new OAuth/OIDC identity, `sessionCookieUserId` falls back to reading the raw cookie when `auth()` reports nobody, so the shared-device rule still sees an ended session's user: `sessionCookieSubject` (`src/server/lib/session-cookie.ts`) decodes it with Auth.js's `getToken` and the secrets Auth.js uses (`AUTH_SECRET`, else `NEXTAUTH_SECRET`, else `AUTH_SECRET_3..1`), from the request's `cookie` header only, under the one name Auth.js uses (`__Secure-` when `AUTH_URL`/`NEXTAUTH_URL` is https, or without either when `x-forwarded-proto` includes https, as Next.js reads it), so a leftover cookie of the other name, which signing out can't clear, refuses nobody; its test runs against Auth.js's real `encode`
- `src/server/lib/auth-config.ts` — Parses sign-in env vars (`OIDC_*`, `GOOGLE_*`, `EMAIL_SERVER_HOST`, `DISABLE_PASSWORD_LOGIN`) into `AuthConfig`; invalid values fall back to defaults with a logged warning. `auth.getLoginOptions` turns it into the login page's buttons (password form, magic link, OIDC, Google), plus `passwordReset` (`passwordLogin && magicLink`), which tells `/forgot-password` whether it can email a link or must send the user to an admin
- `src/server/lib/oidc-sign-in.ts` — OIDC sign-in policy: `decideOidcSignIn` (pure allow/deny) + `gatherOidcFacts` (DB lookups) + `checkOidcSignIn` (both, plus the `auth.oidc_denied` log), which `auth.ts`'s `signIn` callback delegates to; denials redirect to `/login?error=<code>` (mapped to messages by `src/lib/sign-in-errors.ts`)
- `src/server/lib/sign-in-identity.ts` — What the OIDC and Google sign-ins share: `findLinkedUserId`, `findSignedInUserId` (a session whose user row is gone counts as signed out, as in Auth.js), `isSessionConflict` (the shared-device rule: a sign-in that isn't the signed-in user's own is refused, since Auth.js would link a not-yet-linked identity to them), and `readEmailVerified` (read by the Google policy, and by `auth.ts` for OIDC). `auth.ts`'s `jwt` callback ends the session when the password version differs or can't be read (#397); `sessionCookieUserId`'s raw-cookie fallback still sees that user for `isSessionConflict`
- `src/server/lib/google-sign-in.ts` — Google sign-in policy, same shape as the OIDC one (`checkGoogleSignIn` is what `auth.ts` delegates to; `src/server/auth.test.ts` covers both providers' wiring). Refuses a Google sign-in that isn't the signed-in user's own (`GoogleSessionActive`, `isSessionConflict`). A Google account already linked signs in. A new one needs an email Google has verified (`GoogleEmailUnverified`), one no ShareTab user has in any letter case (`GoogleAccountExists`: Google never links), for `ADMIN_EMAIL` an address Google is authoritative for (`@gmail.com`, or the `hd` claim of a Workspace or Cloud Identity domain: `GoogleAdminEmailNotHosted`, since Google keeps other addresses verified after the mailbox changes hands and `ADMIN_EMAIL` grants admin by address), and Registration Mode _Open_ (`GoogleRegistrationDisabled`; invite-only counts as closed, `DISABLE_PASSWORD_LOGIN` doesn't). Google doesn't count for the `DISABLE_PASSWORD_LOGIN` lockout guard, since it never links to an existing account. The OIDC policy never links an account that has a Google identity (`already_linked` counts any `Account` row; only OIDC and Google sign-ins create them). `auth.ts` registers Google with `googleProviderOptions` (pinned `GOOGLE_PROVIDER_ID`, `prompt=select_account`), which `src/server/google-provider.test.ts` runs through the real Auth.js with Google's endpoints stubbed (the authorization URL, what the `signIn` callback gets back, and that a refused or failed sign-in creates no user and starts no session). The login page's `sessionActive` error offers a Sign out button. `GoogleEmailUnverified` and `GoogleAdminEmailNotHosted` have their own login-page messages, since trying again can't help
- `src/server/lib/registration-mode.ts` — `readRegistrationMode` (the admin Registration setting; no setting or an unknown value reads as `open`), used by `auth.register` and `auth.getRegistrationMode`, which also close the register form while password login is off; `REGISTRATION_MODES` validates the admin setter (`admin.getRegistrationMode` reads through `readRegistrationMode` too); `isRegistrationOpen` for the Google policy, which reads the setting as is, and the OIDC policy, which reads it only for email linking while password login is on
- `src/server/lib/password-login.ts` — Credentials `authorize` (rate limits, case-insensitive lookup, bcrypt check; returns the `passwordChangedAt` read with the hash it verified), the per-address login limit (`loginRateLimitKey`, `loginAttemptsPerEmail`, `LOGIN_WINDOW_MS`), whose count and window Settings guesses reuse under a key of their own (`passwordChangeGuessKey`), and `requirePasswordLogin`, which refuses the password routes while password sign-in is off
- `src/server/lib/password-reset.ts` — Password reset links (#397): a 256-bit token in the link's fragment (`src/lib/password-reset-link.ts`, `/{locale}/reset-password#token=…`), stored only as its SHA-256 hash. `PasswordResetToken.userId` is unique: a user has at most one link. Issuing one (`issuePasswordResetToken`) locks the user row (`FOR NO KEY UPDATE`, then `canResetPassword` on the locked row) and upserts, so a user suspended meanwhile gets none. `resetPasswordWithToken` turns away an unknown or expired link before opening a transaction; then, in one transaction, it locks the user row the same way, claims the link by deleting it by hash, and only then bcrypt-hashes the new password, so a link sent many times at once costs one bcrypt and works once, and stamps `passwordChangedAt` after the hash (the new password version, `auth.ts`). Its transactions, issuing a link's and `auth.changePassword`'s run through `passwordTransaction`, which reports a full pool or timed-out transaction (P2028) as SERVICE_UNAVAILABLE `serverBusy`. Lock order is the user row, then the token row: `auth.changePassword` (one transaction that updates the password only while it is still the one just checked, else CONFLICT `passwordChangedElsewhere`, then deletes the link), `admin.suspendUser` and `admin.deleteUser` follow it, and all three delete the link. `auth.changePassword` counts each current password it checks (`passwordChangeGuessKey`, `password-change:<userId>`: the same count and window as the per-address login limit, `AUTH_RATE_LIMIT_MAX` in 15 minutes) before the bcrypt compare, so guesses sent at once are held too; a right one, or a reset, clears the count. A counter of its own, so someone filling an address's login bucket can't block its owner's change. `requirePasswordLogin` (`password-login.ts`) refuses the change, both reset routes and `admin.createPasswordResetLink` while password sign-in is off. `emailPasswordResetLink` makes at most `RESET_EMAILS_PER_ACCOUNT` (5) links an hour per account (main rate-limit store, keyed by user id), quietly skipping the rest; a link whose email fails still counts (it replaced the user's last one), and only a request that made no link is given back. It warns when the link would point at localhost (`auth.password_reset_link_localhost`) or use plain http (`auth.password_reset_link_insecure`). `emailPasswordChanged` tells the account its password changed, after a reset or a Settings change, when email is configured. Router side: `auth.requestPasswordReset` (needs password login and email) answers the same for every address and doesn't wait for the email, so neither the answer nor its timing tells whether an account exists; per IP it allows 20 requests an hour, `auth.resetPassword` 30 submissions in 15 minutes (both skipped without a client IP header; `PASSWORD_RESET_RATE_LIMIT_MAX` sets both, and docker-compose and the Unraid template pass it, empty for the defaults). Failed sends are logged through `describeMailError` (`mailer.ts`). A reset or Settings change clears that address's login rate limit (`loginRateLimitKey`, `clearRateLimit`); the Settings page then signs in again with the new password as the user `auth.changePassword` names (`signInAs`: none while an admin impersonates, whose own session stays) and says so if it can't. `admin.createPasswordResetLink` (audit-logged `PASSWORD_RESET_LINK_CREATED`) returns a 24-hour token that the admin page, after a `ConfirmDialog`, turns into a link from its own address, the way back in on an instance without email. Once a link is used, the reset page replaces its token in the address bar with `#done`, so switching language or reloading shows the outcome. The emails' text is in `messages/{locale}/emails.json` (server-only, read by `password-reset-email.ts`)
- `src/server/lib/mailer.ts` — SMTP settings shared by every sender (`smtpOptions` for the magic-link provider, `createMailTransport`, `mailFrom`, which treats an empty `EMAIL_FROM` as unset), `publicBaseUrl` (the origin of `AUTH_URL`, then `NEXTAUTH_URL`; one that isn't an http(s) URL throws, logged as `mail.public_url_invalid`) for the links in password and auth-expiry emails, never the request's Host header (Auth.js builds magic links itself), and `describeMailError` (what to log about a failed send: nodemailer's code, SMTP response code and command, never the message)
- `src/server/lib/admin-email.ts` — Who the admin is (#399): `isAdmin(db, user)`, used by the app layout's Admin link, `adminProcedure` (with the real admin while impersonating), both handlers of `/api/admin/impersonate` and `/api/admin/export`. `ADMIN_EMAIL` matches ignoring letter case and surrounding spaces, picking the account as `findUserByEmail` does: an exact match needs no lookup, an other-case one is the admin only when no other account has the address (legacy case-duplicate accounts: the exact one, or with none nobody, logged `admin.email_ambiguous`). `isAdminEmail(email, adminEmail)` is the pure address match the Google policy uses
- `src/server/lib/user-email.ts` — Case-insensitive user lookup by email (`findUsersByEmail` / `findUserByEmail`), shared by the Auth.js adapter, password login, `auth.register`, the OIDC and Google policies, password reset emails, and the admin check (`admin-email.ts`)
- `src/server/lib/env.ts` — `parseBooleanValue`: the boolean env vocabulary (true/1/yes/on, false/0/no/off) shared by `auth-config.ts` and `guest-uploads.ts`
- `src/server/lib/guest-uploads.ts` — Guest receipt upload kill switch: admin toggle (`guestUploadsEnabled` SystemSetting, default on, cached 10s, save via `saveGuestUploadsSetting`) overridden by `DISABLE_GUEST_UPLOADS=true` (the admin save is refused while it is set; an unrecognized value logs a warning and is ignored). When off, `canUseGuestUploads` refuses anonymous callers at `/api/upload?guest=true` (403) and `guest.processReceipt` (FORBIDDEN); signed-in users with an active (not suspended) account share the Quick Split path and keep access
- `src/server/lib/guest-join-limit.ts` — `checkJoinRateLimit` for `guest.joinSession`: 10 joins/min per person (share token + the caller's person token when it sends one, else + normalized name) and 200/min per share token (twice the 100-person session cap). The session budget is peeked before the person budget is spent, so a refused call consumes nothing. A client rotating names can use up the per-token budget (accepted, like the other per-token guest limits)
- `src/server/lib/guest-session-limits.ts` — `checkClaimWriteRateLimit` for `claimItems`, `editPersonName`, `removePerson` and `splitClaimItem`: per kind of change, 30/min per person (share token + the caller's person token) and 300/min per share token, the session budget peeked before the person budget is spent as in `checkJoinRateLimit`. The person token is only checked against the session inside the transaction, so a client sending made-up tokens is held only by the per-token budget. `checkSessionReadRateLimit` for `getSession`: 3000/min per share token (100 open claim pages polling every 3 s make 2000). The claim page keeps polling after a failed read, every 15 s, and keeps a loaded session on screen unless the read says it's gone (`claimPollInterval` / `isSessionLost` in `src/lib/guest-session.ts`)
- `src/server/lib/guest-people.ts` — Claim-session people and their stable public `id`: a person's array index shifts when someone listed before them is removed, so the claim-session mutations take people only by id (`claimItems` `personId`, `removePerson`/`editPersonName` `targetId`, `finalizeSession` `personId`; an unknown id is CONFLICT). The old index inputs were removed (#225): an index could name whoever moved into that place. E2e tests read ids from `joinGuestSession` or `personIdByName` (`e2e/helpers.ts`). `createClaimSession`/`joinSession` mint ids; people saved without one get theirs the first time `getSession`, `resumeSession` or `joinSession` loads them. A person also keeps `saves`: the last 10 `claimItems` save keys their token sent, each with a 16-character digest of its changes (read through `validSaveRecords` in `json-schemas.ts`, which skips malformed records); `claimItems` answers a key it already has as stored without applying it again, even once the split is finalized, and refuses the same key with other changes (CONFLICT) (#238). No tRPC procedure returns `saves` (the admin export dumps whole rows, tokens included)
- `src/server/lib/receipt-limits.ts` — Receipt upload and AI scan limits (#434), hourly in the main rate-limit store: per signed-in account on the group scan path (`USER_UPLOAD_LIMIT` in `/api/upload` without `?guest=true`; `USER_AI_LIMIT` in `receipts.processReceipt` and `retryProcessing`, which share it), the guest scan limits (`guestScanQuotas`: 3 per receipt, 20 per client IP, `GUEST_AI_GLOBAL_LIMIT`), and `AI_GLOBAL_LIMIT`, which every receipt scan spends, guest or signed in (not the admin provider test): a scan on the group scan path (`receipts.processReceipt` / `retryProcessing`) skips the guest cap but still stops at this one, so it bounds the instance's AI spend. It caps guest scans too, and since each key's window starts at its own first spend (a refunded spend still opens one), guests can take up to twice `GUEST_AI_GLOBAL_LIMIT` of one `AI_GLOBAL_LIMIT` window: all of it at the defaults. `spendBudget` spends from every quota or none, after the access check and before the processing claim, and returns a refund the scan procedures call when the claim finds the receipt already being scanned. Guest uploads keep their own limiter in the route
- `src/server/lib/receipt-processor.ts` — `processReceiptImage`: the receipt-scan pipeline shared by signed-in and guest scans (reads the image, runs `getAIProvidersWithFallback`, normalizes the date, creates the receipt items)
- `src/server/lib/auth-health-poller.ts` — Background poller (started from `src/instrumentation.ts`) that checks Meridian and ChatGPT OAuth health when those providers are configured and emails `ADMIN_EMAIL` when auth expires (needs `EMAIL_SERVER_HOST`)
- `src/server/lib/meridian-login.ts` / `openai-codex-login.ts` — OAuth PKCE login flows behind the admin dashboard's Meridian and ChatGPT sections; credentials persist in `CLAUDE_DIR` / `OPENAI_CODEX_DIR` (`/app/claude`, `/app/chatgpt` in Docker); both read token-endpoint answers through `src/server/lib/oauth-token-response.ts` (`describeTokenError` keeps only the status and an RFC 6749 error code, `readTokenBody` fails with a fixed `Malformed token response`), so token-endpoint text never reaches errors, logs or audit entries
- `src/server/lib/logger.ts` — Structured logger honoring `LOG_LEVEL`, with an in-memory buffer (`getRecentLogs`) that feeds the admin Server Logs section
- `src/server/lib/build-info.ts` — `getBuildInfo`: `package.json` version plus the commit SHA baked in at build time (`COMMIT_SHA` build arg → `.commit-sha`)
- `src/server/lib/normalize-date.ts` / `upload-dir.ts` — Receipt date normalization to `YYYY-MM-DD`; `UPLOAD_DIR` resolution
- `src/server/lib/guest-transaction.ts` — `guestTransaction`: runs a claim-session transaction at Repeatable Read through `withTransactionRetry`; each transaction must read and write only the one `GuestSplit` row it looks up, and may run more than once (keep side effects outside it). A conflict that outlasts the retries becomes a generic `CONFLICT` error. A Prisma transaction manager error (`P2028`, which covers several transaction lifecycle failures, e.g. no pool connection within `maxWait` or the transaction running past its `timeout`) becomes `SERVICE_UNAVAILABLE` with no retry, since retrying the pool case adds load while the pool is full. `passwordTransaction` (`password-reset.ts`) maps it the same way for the password and reset-link writes; other routers' `$transaction` calls don't map it yet
- `src/server/lib/transaction-retry.ts` — `withTransactionRetry`: re-runs a transaction that Postgres aborted with a serialization failure or deadlock (40001 / 40P01, seen through `@prisma/adapter-pg` as P2034 or `TransactionWriteConflict`), up to 10 runs with capped, jittered backoff
- `src/server/lib/rate-limit.ts` — In-memory rate limiter: `checkRateLimit` (consume), `peekRateLimit` (check without consuming), `refundRateLimit`, `clearRateLimit` (forget a main-store key); `parsePositiveInt` reads env limits so a non-numeric value falls back to the default instead of disabling the limiter. Counters reset on restart. Two stores: the main one (login, registration, per-IP, per-user and global counters) never evicts; `checkTokenRateLimit` / `peekTokenRateLimit` use a separate store for keys built from a client-sent share token, person token or receipt id before it's checked, capped at `MAX_RATE_LIMIT_KEYS` (50,000) with O(1) oldest-window eviction, so minting keys can't grow memory without bound or evict the main store's counters. Every guest procedure caps its share token at 64 characters (`shareTokenSchema` in `guest.ts`) before a key is built from it
- `src/server/lib/client-ip.ts` — `getClientIp`: `cf-connecting-ip`, then `x-real-ip`, then the first `x-forwarded-for` entry; returns `FALLBACK_IP` (`'global'`) when none is set (login and the password reset limits then skip their per-IP bucket; guest endpoints share it as one bucket). Under `next start` / standalone this doesn't happen in practice: Next.js fills in `x-forwarded-for` with the socket address when it's missing, so a proxy that forwards no client address puts every user in one per-IP bucket. The headers are spoofable without a trusted reverse proxy
- `src/server/lib/exchange-rates.ts` — `getExchangeRate(from, to, date?)` from frankfurter.app (ECB rates, no API key), cached in memory for 1 hour; returns `null` on failure. Used by the expenses, settlements, and receipts routers to convert into the group's currency; on `null`, each asks for a manual rate (the receipt page opens its rate field on `exchangeRateUnavailable`, #361)
- `src/server/lib/app-error.ts` — `AppError(code, key?, values?)`, the error every procedure throws (#266): `key` names its text in `messages/{locale}/errors.json` (a server-only namespace, not loaded into pages), and init.ts's `errorFormatter` (`errorShape`) sends it in the language of the page that called, with the key as `data.messageKey`. Its `message` stays English for logs, tests and API callers that send no language. An error without a key, including an unexpected exception or input that fails zod validation, reaches the person as the general message for its code, never its own text. `detail` passes an outside system's text through as it came (an AI provider's or the OAuth login's error, on the admin pages). `errorText` gives a key's text for answers that aren't tRPC errors (`/api/upload`)
- `src/lib/locale-header.ts` — `x-locale`: the page's language (its `<html lang>`), sent by the tRPC links in `providers.tsx` and by the receipt uploads; `localeFromHeader` reads it on the server, falling back to `en`. The browser's `Accept-Language` is the browser's language, not the one chosen in ShareTab
- `src/server/lib/json-schemas.ts` — Zod schemas and `parse*` helpers for JSON columns (receipt extracted data; guest split items, people, assignments); validate with these instead of casting. `receiptCurrency(extractedData, fallback)`: a receipt's currency (#361). The scan saves the currency it reads, or the group's when it can't tell (`processReceiptImage`'s `fallbackCurrency`; USD outside a group), and `getReceiptItems`, `listPending` and `assignItemsAndCreateExpense` resolve a missing one to the group's. The receipt page changes it with `receipts.setCurrency` (under the receipt's row lock; refused unless the scan completed, or once it has an expense), and Create Expense sends the currency it showed (`expectedCurrency`, checked again under the `FOR SHARE` lock, `receiptChangedElsewhere`) and an optional hand-entered `exchangeRate`
- `src/server/lib/signed-cookie.ts` — HMAC-SHA256 `signPayload` / `verifyAndParse` (keyed by `AUTH_SECRET`, falling back to `NEXTAUTH_SECRET`), used for the admin impersonation cookie
- `src/server/lib/strip-undefined.ts` — `stripUndefined`: drops `undefined`-valued keys so optional zod output fits Prisma input types under `exactOptionalPropertyTypes`
- `src/lib/venmo.ts` — Venmo handle normalization and pay deep links. Venmo pay links and the split page's handle input show only when the `venmoEnabled` SystemSetting is `'true'` (admin toggle, default off) and the currency is USD; the handle field in Settings always shows
- `src/lib/guest-session.ts` — Claim-session identity helpers shared by client and server: `normalizeGuestName`, `isGuestSessionToken`, `storedClaimIdentitySchema` (the identity kept in localStorage) with `getStoredClaimIdentity` / `setStoredClaimIdentity` / `removeStoredClaimIdentity` (Quick Split's and the group scan page's Share Link store the creator's identity, from `createClaimSession` with `joinCreator`, before opening the claim page, #263; they send `joinCreator` only when `canStoreClaimIdentity`, since a creator whose token can't be stored couldn't resume it or join under that name), idempotency keys (`newRequestKey` for join and save keys, `joinKeyFor`), `resumeOutcome` (what a device does with a stored token or a personal link), `canAdoptAnswer` (whether a join or accepted personal link may still be adopted: another tab of the browser may have stored someone else while it was in flight), the personal-link hash helpers (`personalLinkHash` / `readPersonalLinkToken`, `…/claim#me=<token>`), and `needsMembershipCheck` (when the claim page asks the server whether its person was removed)
- `src/lib/group-size.ts` — How many people a claim-session person stands for (`MIN_GROUP_SIZE`–`MAX_GROUP_SIZE`, 1–20, the range `guest.joinSession` and `editPersonName` accept; it weights their share of the items they split, `groupSizeWeights`). The claim page's join and edit forms keep the field's text as typed, so it can be cleared and typed again (#410), and read it with `parseGroupSize` when the field loses focus and on submit: an empty field or a value out of range is refused with a message, not changed. The join form shows who a size over 1 stands for ("You and 1 other person") before joining
- `src/lib/avatar.ts` — Shared avatar color and initials helpers
- `src/lib/currencies.ts` — Currency list for the currency selector, plus `DEFAULT_CURRENCY` (USD) and `currencyCode(value)` (an uppercase ISO 4217-shaped code, or undefined), which the scan schema and `receiptCurrency` use (#361)
- `src/server/ai/providers/mock.ts` — Deterministic `mock` AI provider: accepted by `AI_PROVIDER_PRIORITY` but not listed as a selectable provider or in the admin test UI; CI runs the build and e2e suite with `AI_PROVIDER_PRIORITY=mock`
- `src/server/trpc/init.ts` — tRPC context, `publicProcedure`, `protectedProcedure`, `groupMemberProcedure`
- `src/server/trpc/router.ts` — Root app router (exports `AppRouter` type)
- `src/server/trpc/routers/` — Individual routers: auth, groups, expenses, balances, settlements, activity, receipts, guest, admin
- Deleting and restoring expenses and payments (#327): `expenses.delete` and `settlements.delete` set `deletedAt` and `deletedById` (relation `onDelete: SetNull`) instead of removing the row, so its shares and receipt stay; `expenses.restore` and `settlements.restore` clear them. Reads that list records or work out balances spread `notDeleted` (`src/server/lib/soft-delete.ts`) into their where: `loadGroupBalances` (and so the archive, delete, leave and removal checks, and both restores' checks for someone no longer in the group), the dashboard balances, `expenses.list`, `settlements.list` and the groups lists' expense counts. The rest still count deleted rows, since the row still names its people and its receipt and can come back: the history checks (`isInGroupHistory`, a placeholder's), the group currency lock (a restored expense keeps its conversion to the old currency), placeholder merges, the receipt checks (a deleted expense keeps its receipt and the receipt's item assignments, so the receipt doesn't return to the saved receipts), the admin counts, totals and export, and `expenses.get`. `ExpenseShare` has no `deletedAt`: a read of shares that must skip deleted expenses filters on `expense: notDeleted`. `src/server/lib/soft-delete.test.ts` counts matches of a few read patterns in each file under `src/`, so a file whose count changes fails it until its count is updated; its entry's `why` should then say whether deleted rows count (the test checks only the count). Restore takes the delete permission (expense: creator, payer or owner/admin; payment: payer or owner/admin), checked again on the row read under its lock since a placeholder merge can move who paid or added it, refuses an archived group (`lockActiveGroup`, then the row `FOR NO KEY UPDATE`), and checks what creating the record checks: a payment's two people need membership rows, and with someone removed it may only settle their balance (`requireSettleableParties`, shared with `settlements.create`); an expense naming someone no longer in the group is restored only when it moves their balance toward zero without crossing it (`restoreExpenseFormerMember`), since deleting an old expense can give someone removed at a zero balance a balance again, which restoring it settles. Two such checked writes at once (two restores, or a restore and a payment recorded or restored) can each pass, as two such payments can. Editing a deleted expense is refused (`editDeletedExpense`, also under the row lock), and deleting one again is NOT_FOUND. Nothing purges deleted rows; deleting the group does, and a placeholder merge deletes the payments between the two people, deleted ones included. Both lists take `deleted: true`, which the group page's Deleted expenses and payments section (`src/components/groups/deleted-records.tsx`) reads: an expense opens its page, which shows who deleted it and offers Restore; a payment is restored from the section. `EXPENSE_RESTORED` and `SETTLEMENT_RESTORED` are logged like the deletes.
- Expense history (#326): `expenses.list` pages within one group, ordered by `expenseDate` descending then `id` descending so equal dates have a stable order. `nextCursor` is an opaque token of the first unseen expense's `expenseDate` and `id` (the extra row fetched with `limit + 1`), and the next page filters on those values (`expenseDate` earlier, or equal with `id` no greater) rather than Prisma's `cursor`, which looked the row up, so deleting or re-dating that expense between pages no longer ends the history or skips expenses (#478); a token it didn't issue is BAD_REQUEST. Its optional `search` is trimmed, capped at 1,000 characters, refuses a NUL byte, and matches title or description (notes) case-insensitively, with `\`, `%` and `_` escaped so they match literally (#479). The group detail page uses an infinite query (10 at a time) with a 300 ms debounced search in the query key; changing the search starts a separate result set, and the last result stays on screen, dimmed, while the new one loads (`keepPreviousData`). Older pages load only from the Show more expenses button, not on scroll: Payments sits below the list, and scroll loading put the whole history in front of it (#477). A failed older page is reported next to that button, which retries it; a failed first page or refetch is reported above the list with Retry. Archived groups keep the same history and search. `expenses.test.ts` covers the query `expenses.list` builds, its cursor token and validation, and membership; `e2e/expense-history.spec.ts` covers real-database ordering, cursors that outlive a deleted or re-dated expense, literal search characters, and paging and search on the page.
- `src/server/lib/balance-calculator.ts` — Pure functions for debt simplification and balance computation (extracted for testability)
- `src/lib/split-calculator.ts` — Per-person totals for item splits: `calculateSplitTotals` (Quick Split and claim sessions), `calculateClaimTotals` (the claim page, which shows what items still unclaimed carry), and `calculateReceiptSplitTotals` (#364), which the group scan page previews and `receipts.assignItemsAndCreateExpense` saves from. Both use the list the page builds with `receiptAssignmentList` and sends with Create Expense and Save for later: the current items that have someone (#411), in receipt order, each with its people in the order the page holds them. That order decides who takes a leftover cent two people have equal claim to (#331). In `calculateSplitTotals` tax and tip follow each person's item total, so a person whose items come to nothing or less (the guest API takes a negative price) pays none of either; when everyone's do, they're shared by head, a group counting for its size. Tax and tip are shared over the prices of the items assigned, not the subtotal the scan read, so the mutation refuses a receipt with an item nobody has, or with no items (`receiptItemsUnassigned`), and an item not on the receipt (`itemNotOnReceipt`). It reads the items inside its transaction, after its `FOR SHARE` lock on the receipt's row, and refuses a receipt being scanned again (`receiptNotReady`). The page also sends each person's total as it showed it (`expectedShares`, optional for API callers, which showed no split). When it's sent, the mutation saves only that split, and refuses a receipt that changed since the page loaded it with `receiptChangedElsewhere`: an item repriced, added or deleted (in place of the two refusals above). An item deleted after the items are read but before its assignments are written gets that refusal too, from API callers as well; one deleted later waits for the expense and lands after it, as a new price does. After a refused Create, Save for later or item delete the page reloads the receipt
- `src/lib/expense-split.ts` — What the expense form's Shares and Percentage editors save (#331): `sharesSplitShares`, `percentageSplitShares` (null until the percentages add up to 100% within `percentTolerance`, which widens with the people above 0% since stored basis points can each be 0.005 off; the amount follows the basis points, so that difference is spread rather than landing on one person) and `evenPercentages`, the Percentage editor's opening values (7 people: four at 14.29%, three at 14.28%). Each row of the Shares editor, and of the Percentage editor once the percentages add up, shows the amount that's saved
- `src/server/lib/group-balances.ts` — `loadGroupBalances(db, groupId)`: loads one group's expenses and settlements that aren't deleted (`notDeleted`, #327) and runs `computeBalances`; shared by `balances.getGroupBalances`/`getSimplifiedDebts` and `requireSettledUp`, among others, so the group page and the archive and delete checks agree. `requireSettledUp(tx, groupId, keys)`: refuses (PRECONDITION_FAILED) a group where any net balance is nonzero, with a separate message when one belongs to someone with no membership row (a user who left before #323, who must rejoin before a payment can settle it, or an account an admin deleted before then); someone removed from the group still counts as a member here. `groups.archive` and `groups.delete` call it once they hold a lock that waits for the writes taking `lockActiveGroup`; a placeholder merge takes no group lock, and besides moving a balance between two people it re-rounds converted-currency expenses (a tied cent can land on someone else), so one landing mid-read can make the check refuse a settled group or pass one a few cents out. `lockActiveGroup(tx, groupId, message)`: the first statement of every transaction that changes a group's balances (expenses create/update/delete/restore, settlements create/delete/restore, `receipts.assignItemsAndCreateExpense`) locks the group's row `FOR SHARE` and refuses an archived group. `groups.archive` sets `archivedAt` before reading the balances, in one transaction, so its update waits for those writes and they wait for it (#289). Each of those writes checks that the people it involves are members after taking the lock, and `groups.removeMember` takes `lockGroupMembers` (`FOR NO KEY UPDATE`) before its balance check and the removal, so a member can't leave with a balance written in at the same moment (#279). A new write that changes balances must do both. `removeMember` then locks the person's own membership row `FOR NO KEY UPDATE`, since a placeholder merge into them takes no group lock, only a share lock on that row (#323). `groups.transferOwnership` takes `lockGroupMembers` too, and both it and `removeMember` read the roles they decide on after the lock, so a transfer racing a removal, a leave or a second transfer can't leave the group with no owner or two (#309); the old owner becomes `MEMBER` (nothing assigns `ADMIN`). `groups.delete` also re-reads the caller's role after `lockGroupMembers`, so a delete the old owner sent while handing the group over is refused, then refuses while anyone in the group owes money (`requireSettledUp`, #390): deleting would take every open balance with it, for everyone, with no way back. `admin.deleteGroup` doesn't check balances (its dialog says they go too): it is how an instance's operator clears a group out regardless. `groups.addPlaceholder` and `renamePlaceholder` take `lockGroupMembers` too and refuse a name another member already has, compared with `normalizeGuestName` (#265)
- `src/server/lib/placeholder-merge.ts` — `mergePlaceholderIntoUser(tx, …)`: hands a placeholder's expenses, shares, payments and receipt assignments in one group to a member with an account, inside the caller's transaction (`groups.mergePlaceholder`, and `groups.joinByInvite` for an invite made for a placeholder, which group settings offers as "Invite to claim"). Where both were in one expense, `combineShares` adds their amounts and makes the expense an exact split of its stored amounts (a receipt split keeps its mode), since share units or percentages recomputed by the edit form can land a cent away; a payment between the two is deleted, since it would be a payment to themselves. It locks the target's current membership row (`SELECT … FOR SHARE`) and removes the placeholder's membership first, so a removal or a second merge waits for it
- Removing someone from a group (#284, #323): `groups.removeMember` deletes a placeholder who is in no expense or payment. One who is in any goes only at a zero balance (`placeholderUnsettled` otherwise), and only from the member list: `GroupMember.removedAt` is set, and their expenses, shares and payments stay theirs. Someone with an account who leaves or is removed (an owner may remove one with a balance, #279) gets the same mark while this group's expenses or payments name them (`isInGroupHistory`), and loses the row otherwise. `admin.deleteUser` marks every membership of the account it turns into a "Deleted user" placeholder (role `MEMBER`), except in a group it owns that nobody could take over. Joining again by invite brings the row back (`joinByInvite` clears `removedAt` and sets `role` to `MEMBER` and `joinedAt` to now), but not for a placeholder or a deleted account: once it has claimed the invite it locks the account `FOR SHARE`, which also refuses a first join by a placeholder (only possible by impersonation) or by an account deleted while its request was in flight. People with an account who left, or were deleted, before #323 have no row: their balances show without a name until they rejoin, which a deleted account can't. A removed person is not a member for any check of the caller's own membership (`groupMemberProcedure`, the groups lists, dashboards and recent activity, receipt and upload access, sharing a group's receipt into a split (`canOpenReceipt`), and joining by link, where a removed account rejoins and a removed placeholder is refused), any role read (`removeMember`'s caller, `transferOwnership`, `groups.delete`, the next owner `admin.deleteUser` picks), `groups.get`'s `members` (they're in `removedMembers`), an invite's member count, new expenses, receipt expenses and saving a receipt for later, renaming, merge targets (`mergePlaceholderIntoUser` locks only a current row), and claim links (`findPlaceholderMember`, and `mergePlaceholderIntoUser`'s `requireCurrent` on `joinByInvite`). They still count for the names in balances (`removedMembers`, the dashboard's name map), the archive and delete checks (`requireSettledUp`), `groups.mergePlaceholder` (a removed placeholder as the one merged), group deletion (which deletes removed placeholders, deleted accounts included, once no membership, expense, share, payment or admin-audit entry of theirs is left; activity, uploads, splits and invites they made are unlinked; an invite's `usedById` and activity metadata keep the bare id) and name uniqueness, and in `settlements.create` and `settlements.restore` (`requireSettleableParties`), where a payment with them may only settle their balance without crossing zero (`settlementRemovedMemberOverpaid`); `expenses.restore` applies the same rule to an expense naming them (`restoreExpenseFormerMember`, the #327 bullet). Editing an expense keeps them in the part they had, payer or share (`expenses.update` reads who has which under the expense's row lock, `FOR NO KEY UPDATE`), and the edit page shows them only there. Adding a removed placeholder's name again brings them back with their history (`addPlaceholder` returns `restored`), even when someone removed with an account has the same name; a deleted account's name is only taken. Removing a placeholder who stays in the group's history clears them as payer of the group's receipts saved for later and drops their item assignments there; one deleted outright loses every item assignment, but a pending receipt's `paidById` still names them. Admin counts include removed rows. Exceptions, which check the uploader or saver rather than membership: `/api/uploads` still serves the image of a receipt they uploaded; `receipts.deletePending` lets the uploader or saver take a pending receipt off the group; a receipt uploaded outside any group that became one of its expenses (API only) stays open to its uploader through `verifyReceiptAccess` and `canOpenReceipt`. A new read of `GroupMember` has to choose which of these it is
- `src/server/lib/group-delete.ts` / `receipt-cleanup.ts` — Deleting a group or a split takes what only it used (#265). `deleteGroupWithData(tx, groupId)` (`groups.delete`, `admin.deleteGroup`) locks the group's row `FOR UPDATE`, so no new membership or receipt row lands meanwhile (a rejoin restores an existing row, which that lock doesn't stop; the two deadlock and PostgreSQL aborts one) (`addPlaceholder` creates the placeholder and its membership in one write for this), then deletes its receipts that no split uses, the group, and its placeholder members. A receipt is used by its group, its expense, and every Quick Split or claim session made from it (`GuestSplit.receiptId`; the claim page shows its image), so it stays until the last of those goes: `guest.deleteSplit` and `deleteExpiredSplits` (the background cleanup each new split runs, 100 at a time, and the admin dashboard's purge, 500 at a time) delete a split's receipt once no group, expense or other split uses it, locking the receipt rows first so two deletions sharing one can't both keep it. Deleting a receipt from a group's pending list (`receipts.deletePending`) takes it off the group under its row lock and hands it to the same check, so one a claim session made with the group scan page's Share Link uses stays until that split goes (#318), `receipts.assignItemsAndCreateExpense` re-reads the receipt's group under a `FOR SHARE` lock, so an expense can't link one taken off the group meanwhile, and `saveForLater` (which locks the row and checks access again) and `processReceipt` (whose claim updates the row only while it's still in the group its access check saw) can't put it back. The claim page shows its image, so `/api/uploads` serves a receipt to anyone, as it does a guest upload, while an unexpired split made through `lockReceiptForSplit`'s check uses it (`GuestSplit.receiptShared`; splits made before the check stay false). That check takes a receipt only from someone with an active account who can open it on the group's pages (a member of its group, or for one outside a group its uploader); any other is NOT_FOUND. `createSplit` and `createClaimSession` take the lock a foreign key would on the receipt they're made from (`lockReceiptForSplit`), so such a deletion either sees the new split or finishes first and the split is saved without the receipt. Image files are removed with `removeReceiptFiles` once the transaction commits; one that can't be is logged and left for the admin orphan cleanup. Receipts nothing uses that nothing has changed for a day (left behind before #265, or scans never saved to a group or made into a split) are counted in the admin dashboard's Storage Stats and deleted from there (`countUnusedReceipts` / `deleteUnusedReceipts`, `admin.cleanupUnusedReceipts`, #312), in batches that check each receipt again under its row lock; the day's wait leaves alone a scan someone is still splitting, since Quick Split keeps it only in the page, and one being scanned again, which `processReceipt` marks `PROCESSING` first

- `src/lib/claim-save.ts` — How the claim page sends a save (#238). The page builds one request with a `saveKey` (`newRequestKey`); `settleSave` sends it and, while the outcome is unknown (`failedSaveOutcome`: no answer or a 5xx other than 503; on a retry also 409/429/503), sends it again after a jittered backoff (`saveRetryDelay`: 1 s doubling to 15 s, each wait in the upper half of that), each time only once the server answers a reload of the session, so an outage doesn't use up attempts, up to `SAVE_ATTEMPTS`; a stored save then reloads until a reload lands (up to `SAVE_ATTEMPTS`), keeping its changes in the save in flight. After `SAVE_ATTEMPTS` sends without a settled answer while reads work, the page parks the save (`ParkedSave`, #241): its changes stay shown, Save stays enabled, and the page's next Save, for anyone, sends it again with its own key before the newer changes (`saveInOrder`), so a change it stored can't come back under a new key and undo another device's later change. For anyone, because the server keeps a caller's last 10 save keys whoever the saves are for, so newer saves from the page could make it forget a parked one. They refuse URLs that can't be read safely or that node-postgres and Prisma would read differently: an `@` after the host part (an unencoded `/ ? #` in a password, or an `@` in a query value), a stray `%`, an escaped reserved character (`%2F`, `%40`…) in the database name (node-postgres decodes it with `decodeURI`), spaces around it, a space or a stray `%` anywhere in it (node-postgres would re-encode the whole URL, password included), no database name, `?schema=` other than `public` (any of them, since the two drivers may take different ones), a `host`/`hostaddr`/`port`/`user`/`password`/`dbname` query parameter, a Unix socket, an `sslrootcert`/`sslcert`/`sslkey` file node-postgres can't read. Don't map a model to another table name (`@@map`): the guard takes model names as table names, and a test fails on one. ## Key Conventions

- All monetary amounts are stored as integers in cents (e.g., $12.99 = 1299)
- Divide an amount among people with `allocateProportionally` (`src/lib/money.ts`), never by rounding each share and giving the last person the rest (#331): it rounds every share down and hands the leftover cents to the largest remainders, earliest first on a tie, so the shares add up exactly, each is within a cent of its exact value, and a zero weight gets nothing (unless every weight is zero, which splits equally). The shares and percentage editors (through `src/lib/expense-split.ts`), item and tax/tip splits (`split-calculator.ts`), converted expenses' shares (`computeBalances`) and a scan's discount lines folded into its items (`foldDiscountLines`, `src/server/ai/schema.ts`, #507) use it; the equal editor's split is the same one. Changing it changes what `computeBalances` shows for converted expenses already saved, since their group-currency shares aren't stored
- Archived groups refuse new expenses, expense edits, deletes and restores, and settlements (recording, deleting or restoring one). `groups.archive` refuses while any net balance in the group is nonzero, and the dashboard balance queries (`balances.getOverallDebts`, `getDashboard`) deliberately include archived groups, so an open balance in one stays visible on the dashboard: `getDashboard.perGroup` flags `archived`, and the dashboard gives an archived group where the viewer's balance is nonzero its own card. The group page hides the payment actions (Settle, Pay via Venmo) for an archived group (#275), and the group, expense, add, edit and scan pages hide or replace the other actions it refuses (#290). The archive check and the writes it guards serialize on the group row (`lockActiveGroup`, #289)
- tRPC routers live in `src/server/trpc/routers/`
- `protectedProcedure` requires auth; `groupMemberProcedure` requires group membership
- AI providers implement the `AIProvider` interface in `src/server/ai/provider.ts`
- `src/middleware.ts` — NextAuth middleware protecting authenticated routes. It reads the session cookie under the name Auth.js gives it, which follows the scheme of `AUTH_URL ?? NEXTAUTH_URL`, not the request's (`usesSecureCookie` in `session-cookie.ts`, falling back to `x-forwarded-proto` when neither is set), with Auth.js's secrets (`sessionSecrets`): going by the request's scheme sent every page back to the login form behind an HTTPS proxy with an `http://` `NEXTAUTH_URL` (#409). The Auth.js route logs `auth.url_scheme_mismatch` once per direction when a request's scheme isn't that URL's (`src/server/lib/auth-url-check.ts`); the host isn't compared
- `prisma/seed.ts` — Demo data seed script (run with `npm run db:seed`); idempotent — skips if data already exists
- Hand-written SQL, run by `docker/entrypoint.sh` on every start: `prisma/migrations/*.sql` before `prisma db push` (idempotent, and a no-op on an empty database since a fresh install has no tables yet), `prisma/after-push/*.sql` after it (idempotent; log a warning instead of failing, since any error stops startup). `docker/db.mjs` sends each file as one query, so its statements run in one transaction: no `CREATE INDEX CONCURRENTLY` or `VACUUM` alongside other statements, no adding an enum value and using it in the same file (55P04; use two files), no psql meta-commands or `:variables`. `prisma/after-push/user_email_lower_unique.sql` holds the unique index on `lower(email)` that Prisma's schema can't express; `prisma db push` leaves it alone. `scripts/docker-smoke.sh` boots the image on an empty volume to test both phases, then again against `postgres:16-alpine` in its own container (TLS only, self-signed certificate, `sslmode=no-verify`)
- Prisma v7: datasource URL is configured in `prisma.config.ts`, not in `schema.prisma`
- Prisma v7: PrismaClient requires `@prisma/adapter-pg` adapter in constructor
- Prisma v7: import from `@/generated/prisma/client` (not `@/generated/prisma` — no index.ts)

Open it from state (`open={removeFor !== null}`, clearing the state on close); it keeps the text it was opened with while it animates closed. E2e tests click its buttons inside `getByRole('alertdialog')`

## Responsive Layout Architecture

- **Sidebar**: hidden below `lg` (1024px), visible at `lg+` with `lg:sticky lg:top-0 lg:h-dvh`; `overflow-hidden` + `overflow-y-auto` on nav + `shrink-0` on bottom section
- **Outer container**: `min-h-dvh lg:flex lg:h-dvh lg:flex-row` — block flow on mobile (natural scroll), flex on desktop (contained scroll)
- **Main**: `@container flex-1 min-w-0 lg:overflow-auto` — container query context; natural scroll on mobile, contained scroll on desktop
- **Content**: `w-full py-4 px-4 md:py-6 md:px-8 2xl:mx-auto 2xl:max-w-5xl` — full width with padding, max-width only at 2xl+
- **Card grids**: use CSS container queries (`@2xl:grid-cols-2`) NOT viewport breakpoints (`lg:grid-cols-2`) — they adapt to actual available space regardless of sidebar
- **Uniform card lists**: use auto-fit grids `grid-cols-[repeat(auto-fit,minmax(280px,1fr))]` — no breakpoints needed
- **Mobile header**: `lg:hidden` with frosted glass (`backdrop-blur-md`); uses Sheet for hamburger menu
- **Never** use `overflow-hidden` on layout containers — it clips content

## i18n

- Uses `next-intl` with `createNextIntlPlugin` in `next.config.ts`
- 9 locales defined in `src/i18n/routing.ts`: en, es, sv, fr, de, pt-BR, ja, zh-CN, ko (default: en)
- All routes under `src/app/[locale]/` — the `[locale]` segment is required
- Translation files: `messages/{locale}/{namespace}.json` (namespaces: admin, auth, common, dashboard, expenses, groups, settings, split, splits, errors, emails). A new namespace the pages use also needs an import in `src/i18n/request.ts` and an entry in `src/types/next-intl.d.ts`; `errors` and `emails` are read only by the server (`src/server/lib/app-error.ts`, `src/server/lib/password-reset-email.ts`), so they have neither
- Use `useTranslations(namespace)` in client components, `getTranslations(namespace)` in server components
- Locale-aware navigation: import `Link`, `redirect`, `usePathname`, `useRouter` from `@/i18n/navigation`
- `LanguageSwitcher` component in sidebar and mobile menu
- User locale preference stored in `User.locale` field (Prisma schema)
- `npm run lint:i18n` checks for missing or extra translation keys, then parses every message in every locale through `scripts/lib/message-check.ts` with `@formatjs/icu-messageformat-parser`, the parser package next-intl's formatter (`intl-messageformat`) is built on (the lint has its own copy, a devDependency, so the two versions can differ). It fails on:
  - a message that isn't valid ICU, which next-intl would show as its key
  - in a locale with plural forms, a `count` argument (or one named `…Count`) followed by a word outside a cardinal plural on that argument (#441): `{count} items` reads "1 items", so write `{count, plural, one {# item} other {# items}}`, keeping both branches where the word doesn't change (German `Artikel`)
  - in a locale with a `one` form, a cardinal plural without one (with neither `one` nor `=1`, 1 shows in the `other` form); `=1` doesn't stand in for it, since French and Brazilian Portuguese use `one` for 0 too
  - a folder under `messages/` that isn't a language the runtime supports, and a namespace file that isn't valid JSON or isn't a JSON object

  Japanese, Chinese and Korean have one plural form and aren't checked for counts. An apostrophe right before `{`, `}`, `<` or `>` (or `#` inside a plural) starts ICU quoted text, shown as written (`l'{name}` shows "l{name}"), so write `''` for it; the lint only catches that when it leaves the message unparseable. Counts passed under other names (`remaining`, `expired`, `total`) aren't checked either, and a `count` that isn't the number of the word after it (`{count} of {total}`) needs another name. `COUNT_MESSAGES` in `src/i18n/messages.test.ts` lists every English message with a plural (a test fails on one it lacks, unless `NOT_COUNT_MESSAGES` says why) plus messages that show a count under another name, and its snapshot (`src/i18n/__snapshots__/`) records each for 0, 1 and 2 in every locale with plural forms: after changing one, run `npx vitest run src/i18n -u` and read the singulars in the snapshot diff. CI runs lint:i18n; run it locally after changing any `messages/` file

- `src/types/next-intl.d.ts` types `t()` keys against the English messages, so `npx tsc --noEmit` fails on a key that isn't in `messages/en/` (lint:i18n alone only compares the other locales with en)
- To add a new language: add locale to `src/i18n/routing.ts`, create `messages/{locale}/` with all namespace files, add display config to `languageConfig`, add its `Intl` locale to `moneyLocales` in `src/lib/money.ts` (typed `satisfies Record<Locale, string>`, so `tsc` fails until you do), and import its `errors.json` and `emails.json` into the `catalogs` of `src/server/lib/app-error.ts` and `src/server/lib/password-reset-email.ts` (typed `Record<Locale, …>`, so `tsc` fails there too). For a language with plural forms, run `npx vitest run src/i18n` and commit its new section of `src/i18n/__snapshots__/messages.test.ts.snap`, after reading its singulars: CI fails on a missing snapshot

## Docker

All-in-one container: PostgreSQL is bundled inside — no external database required, though setting `DATABASE_URL` uses an external one instead. Requires `NEXTAUTH_SECRET` and `AUTH_SECRET` env vars. `docker/docker-compose.yml` builds the image from the checkout, so upgrading it means `git pull` + `--build`.

Run `npm run test:docker` before pushing a change to `docker/`, the entrypoint, `prisma/` SQL, or dependencies. It builds the image and runs `scripts/docker-smoke.sh`: fresh install on an empty volume, upgrade restarts, a clean `docker stop`, the Meridian provider starting and running through the app (it signs in as an admin and calls the admin "Test Receipt Extraction" endpoint), a stop during the first start and during `pg_ctl start` (made slow by wrappers, so the stop lands inside), a bundled step failing after the server is up, a changed `DB_PASSWORD` taking effect and a changed `DB_USER` or `DB_NAME` waiting with a message instead of restarting (running under `--restart=unless-stopped` with a restart count of 0, a clean `docker stop`, and setting them back works), the README's backup and restore in maintenance mode (a `pg_dump -Fc` restored over an install that changed since, and a plain-SQL dump restored into a fresh one, each compared with the backup table by table), and an external-database section (`postgres:16-alpine`, TLS only with a self-signed certificate: the marker, refusals, a percent-encoded password, a stop during the wait, maintenance mode starting nothing; plus the Compose overlay's database, and a restore into it, when `docker compose` is there). It needs `openssl` and Docker Hub access. Its containers, volumes and network get unique names and publish no ports, so it's safe on a host already running ShareTab; point `DOCKER_HOST=ssh://user@host` at a remote daemon when there's no local Docker (Docker access is root-equivalent on that host). CI runs the same script on pull requests (Docker Fresh Install), and `docker.yml` pushes the image it tested only after the script passes. `--meridian-auth <dir>` adds a live receipt extraction through Meridian using a scratch copy of a Claude login directory on the Docker host (local runs only; needs a token valid for 30+ minutes, and fails if the login was refreshed during the run).

```bash
cd docker && docker compose up -d --build    # Build and start app (PostgreSQL included)
mkdir -p ~/sharetab-backup && docker compose exec -T sharetab su-exec postgres pg_dump -U sharetab -Fc sharetab > ~/sharetab-backup/sharetab.dump  # Backup of the bundled database, outside the checkout (default DB_USER/DB_NAME; with the external-db overlay, dump the postgres service; restoring: README "Restoring a backup")
```
